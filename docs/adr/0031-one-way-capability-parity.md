# ADR-0031：业务侧能力单向对齐开源侧

## 背景

业务侧 Solution 基于本仓库 chat-ui 组件交付，直连塞尔达（MA 对内 API）并自建 nodejs
服务承载 MA 不具备的能力（会话置顶、Solution 级品牌等）。最初按「两侧功能一致」双向
理解，但开源侧部分能力（usage、files、管理端等）绑定 Kit server 数据面，业务侧没有
对应数据源，双向一致不成立也不必要。

## 决策

能力一致性单向：**业务侧功能集 ⊆ 开源侧功能集**。

- 业务侧新增或已有的能力，开源侧必须提供对应支持：合同同构，落点各自适配。
- 开源侧多出的能力，不要求业务侧跟进。

首个落地项：会话置顶与 Solution 级品牌——业务侧落 nodejs 服务，开源侧落 Kit server
本地库，两侧对前端的合同（SDK / chat-ui 数据形状）保持同构。

## 理由

- 单向规则把「一致」从无限对齐收敛为可执行义务：业务侧每提一个能力，开源侧清单加一项。
- 开源侧能力以本仓库 server 与数据面为准绳；业务侧数据源（塞尔达 + 自建服务）天然是其子集。

## 后果

- 业务侧每个新能力都要在开源侧找到落点（Kit server 存储 + chat-ui 合同），工作量计入本仓库排期。
- 一致性由人工对齐保障，合同漂移无机制兜底；若两侧团队分离，需回补功能清单文档。
- 开源侧是否引入 Solution 维度（Solution → Agent → session）仍在确认中；若确认，
  品牌等能力的落点主体随之调整，单向原则本身不变。

## 备选方案

- **双向一致**：业务侧为 usage、files 等自建对应数据面，成本与业务收益不成比例。
- **仅组件合同对齐**：chat-ui props 即合同、服务端各自独立——不满足「业务侧能力
  开源侧也要支持」的交付要求。
